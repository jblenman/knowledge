# mkosi — building bootable Linux disk images (observed 2026-10-16, mkosi 25.3 on Debian 13)

systemd's image builder: a declarative `mkosi.conf` + overlay trees → a GPT disk image with ESP, boot loader, kernel, initrd and root, from distro packages, in minutes. Written while building a Debian image that boots straight into Chrome for a family desktop.

## Layout that worked
- `mkosi.conf` — `[Distribution]` (`Distribution=debian`, `Release=trixie`, `Architecture=x86-64`, `Repositories=main contrib non-free-firmware` — **space-separated lists**, not commas), `[Output]` (`Format=disk`, `ImageId`, `ImageVersion`), `[Content]` (`Bootable=yes`, `Bootloader=grub`, `BiosBootloader=grub`, `KernelCommandLine=`, `Hostname=`, `Locale=`, `Timezone=`, a multi-line `Packages=` list indented under the key).
- `mkosi.extra/` — files laid over the image root after package installation (systemd units, policies, sudoers, repart/tmpfiles definitions).
- `mkosi.sandbox/` — the *build's* package-manager tree: an extra apt source (`etc/apt/sources.list.d/*.sources`, deb822, `Signed-By:` pointing at an armored `.asc` under `etc/apt/keyrings/`) lets `Packages=` name a third-party package (Google Chrome's `google-chrome-stable` from `https://dl.google.com/linux/chrome/deb/`).
- `mkosi.postinst` — runs **outside** the image with it mounted at `$BUILDROOT`; `mkosi-chroot <cmd>` runs inside (users, `systemctl enable`, `passwd --lock root`). Secrets reach it through `--environment KEY=VALUE` on the command line, never from the tree.
- `mkosi summary` parses everything without building; `--incremental` (`-i`) caches the installed tree so script/overlay iterations take a couple of minutes instead of ten; a package-list change invalidates the cache ("Cache manifest mismatch").
- Output: `<ImageId>_<ImageVersion>.raw` (sparse) plus `.vmlinuz` / `.initrd`; the root partition is content-sized with the GPT *GrowFileSystem* attribute set. GRUB EFI lands at `EFI/BOOT/BOOTX64.EFI`; with `BiosBootloader=grub` the image also gets a 1 MB BIOS-boot partition and GRUB's `boot.img` in the MBR. Both paths verified under QEMU (OVMF and SeaBIOS) — ~33 s to userspace under TCG.

## Gotchas met
- **Cross-architecture builds (arm64 host → x86-64 image)** work with `qemu-user-static` + `binfmt-support` installed on the host: apt runs natively, the image's maintainer scripts run under user-mode emulation (a full Debian + Chrome install took ~12 min on an M1 Lima VM with 4 vCPUs).
- **`BiosBootloader=grub` needs `grub-bios-setup` on the *host*** (mkosi only takes the `i386-pc` modules from the image). Debian ships that binary only inside the amd64 `grub-pc-bin` package (`/usr/lib/grub/i386-pc/grub-bios-setup`), and arm64 `grub-common` has `grub-mkimage` but no `bios-setup` → "A BIOS bootable image with grub was requested but bios-setup was not found". Fix on an arm64 host: `dpkg --add-architecture amd64`, install `libc6:amd64 libdevmapper1.02.1:amd64 liblzma5:amd64 libfreetype6:amd64 libfuse3-4:amd64 libefiboot1t64:amd64 libefivar1t64:amd64`, `apt-get download grub-pc-bin:amd64`, extract the binary to `/usr/lib/grub/i386-pc/grub-bios-setup` (a path mkosi checks); it runs under binfmt.
- **Google Chrome's `.deb` post-install needs `apt-config` in the image** (`eval $("$APT_CONFIG" shell …)` → exit 127 without it): put `apt` in `Packages=`. Inside mkosi's sandbox the exported `APT_CONFIG` variable (mkosi's own apt.conf) is then shadowed by the script's `APT_CONFIG=/usr/bin/apt-config`, so apt-config prints `Syntax error /usr/bin/apt-config:44: Extra junk at end of file` — harmless. Pre-seed `/etc/default/google-chrome` with `repo_add_once="false"` and `repo_reenable_on_distupgrade="false"` so Chrome never adds its apt repository to the box.
- **Debian's `systemd-repart` is a separate package**; include it when the image should create or grow partitions at first boot (a `/usr/lib/repart.d/*.conf` with `Type=home` + `Format=ext4` and no size cap becomes a /home partition filling the rest of the target disk, auto-mounted by `systemd-gpt-auto-generator`). Then nothing persistent may live in `/home` inside the image — ssh keys go to `/etc/ssh/authorized_keys.d/%u` (`AuthorizedKeysFile`), home directories come from a tmpfiles.d rule.
- `console=ttyS0,… console=tty1` on the kernel command line makes QEMU tests loggable (`-serial file:`) while tty1 stays the primary console; systemd then also spawns `serial-getty@ttyS0`.
- Chroot-time noise that is not a failure: "Failed to open connection to system message bus", "Failed to preset unit … is masked", `update-alternatives: … bash-builtins.7.gz doesn't exist` (initrd build).

## Headless QEMU testing on a Mac (Homebrew `qemu`)
`qemu-system-x86_64 -machine q35 -cpu max -smp 2 -m 2048 -drive file=test.raw,format=raw,if=virtio -netdev user,id=n0,hostfwd=tcp::2222-:22 -device virtio-net-pci,netdev=n0 -vga std -display none -monitor unix:monitor.sock,server,nowait -serial file:serial.log` (+ for UEFI: `-drive if=pflash,format=raw,readonly=on,file=$(brew --prefix)/share/qemu/edk2-x86_64-code.fd -drive if=pflash,format=raw,file=vars.fd` with `vars.fd` copied from `edk2-i386-vars.fd`). `screendump file.ppm` on the monitor socket + `sips -s format png` gives a screenshot without a window; ssh in through the forwarded port. QEMU's std VGA has no GL, so a wlroots compositor needs `WLR_RENDERER_ALLOW_SOFTWARE=1` to come up there. Always boot a scratch copy of the image, and `truncate` it larger when first-boot partitioning is under test. macOS has no `timeout`; loop with `until ssh … true; do sleep 5; done`.
