# mkosi — building bootable Linux disk images (observed 2026-10-16, mkosi 25.3 on Debian 13)

systemd's image builder: a declarative `mkosi.conf` + overlay trees → a GPT disk image with ESP, boot loader, kernel, initrd and root, from distro packages, in minutes. Written while building a Debian image that boots straight into Chrome for a family desktop.

## Layout that worked
- `mkosi.conf` — `[Distribution]` (`Distribution=debian`, `Release=trixie`, `Architecture=x86-64`, `Repositories=main contrib non-free-firmware` — **space-separated lists**, not commas), `[Output]` (`Format=disk`, `ImageId`, `ImageVersion`), `[Content]` (`Bootable=yes`, `Bootloader=grub`, `BiosBootloader=grub`, `KernelCommandLine=`, `Hostname=`, `Locale=`, `Timezone=`, a multi-line `Packages=` list indented under the key).
- `mkosi.extra/` — files laid over the image root after package installation (systemd units, policies, sudoers, repart/tmpfiles definitions).
- `mkosi.sandbox/` — the *build's* package-manager tree: an extra apt source (`etc/apt/sources.list.d/*.sources`, deb822, `Signed-By:` pointing at an armored `.asc` under `etc/apt/keyrings/`) lets `Packages=` name a third-party package (Google Chrome's `google-chrome-stable` from `https://dl.google.com/linux/chrome/deb/`).
- `mkosi.postinst` — runs **outside** the image with it mounted at `$BUILDROOT`; `mkosi-chroot <cmd>` runs inside (users, `systemctl enable`, `passwd --lock root`). Secrets reach it through `--environment KEY=VALUE` on the command line, never from the tree.
- `mkosi summary` parses everything without building; `--incremental` (`-i`) caches the installed tree so script/overlay iterations take a couple of minutes instead of ten; a package-list change invalidates the cache ("Cache manifest mismatch").
- Output: `<ImageId>_<ImageVersion>.raw` (sparse) plus `.vmlinuz` / `.initrd`; the root partition is content-sized with the GPT *GrowFileSystem* attribute set. GRUB EFI lands at `EFI/BOOT/BOOTX64.EFI`; with `BiosBootloader=grub` the image also gets a 1 MB BIOS-boot partition and GRUB's `boot.img` in the MBR. Both paths verified under QEMU (OVMF and SeaBIOS) — ~33 s to userspace under TCG.

## Gotchas met
- **Cross-architecture builds (arm64 host → x86-64 image)** work with `qemu-user-static` + `binfmt-support` installed on the host: apt runs natively, the image's maintainer scripts run under user-mode emulation (a full Debian + Chrome install took ~12 min on an M1 Lima VM with 4 vCPUs).
- **`BiosBootloader=grub` needs `grub-bios-setup` on the *host*** (mkosi only takes the `i386-pc` modules from the image). Debian ships that binary only inside the amd64 `grub-pc-bin` package (`/usr/lib/grub/i386-pc/grub-bios-setup`), and arm64 `grub-common` has `grub-mkimage` but no `bios-setup` → "A BIOS bootable image with grub was requested but bios-setup was not found". Fix on an arm64 host: `dpkg --add-architecture amd64`, install `libc6:amd64 libdevmapper1.02.1:amd64 liblzma5:amd64 libfreetype6:amd64 libfuse3-4:amd64 libefiboot1t64:amd64 libefivar1t64:amd64`, `apt-get download grub-pc-bin:amd64`, extract the binary to `/usr/lib/grub/i386-pc/grub-bios-setup` (a path mkosi checks); it runs under binfmt.
- **Google Chrome's `.deb` post-install needs `apt-config` in the image** (`eval $("$APT_CONFIG" shell …)` → exit 127 without it): put `apt` in `Packages=`. Inside mkosi's sandbox the exported `APT_CONFIG` variable (mkosi's own apt.conf) is then shadowed by the script's `APT_CONFIG=/usr/bin/apt-config`, so apt-config prints `Syntax error /usr/bin/apt-config:44: Extra junk at end of file` — harmless. Pre-seed `/etc/default/google-chrome` with `repo_add_once="false"` and `repo_reenable_on_distupgrade="false"` so Chrome never adds its apt repository to the box.
- **Debian's `systemd-repart` is a separate package**; include it when the image should create or grow partitions at first boot (a `/usr/lib/repart.d/*.conf` with `Type=home` + `Format=ext4` and no size cap becomes a /home partition filling the rest of the target disk, auto-mounted by `systemd-gpt-auto-generator`). Then nothing persistent may live in `/home` inside the image — ssh keys go to `/etc/ssh/authorized_keys.d/%u` (`AuthorizedKeysFile`), home directories come from a tmpfiles.d rule.
- `console=ttyS0,… console=tty1` on the kernel command line makes QEMU tests loggable (`-serial file:`) while tty1 stays the primary console; systemd then also spawns `serial-getty@ttyS0`.
- Chroot-time noise that is not a failure: "Failed to open connection to system message bus", "Failed to preset unit … is masked", `update-alternatives: … bash-builtins.7.gz doesn't exist` (initrd build).

## First-boot partitions, verified (2026-10-17)
- A runtime definition `/usr/lib/repart.d/20-home.conf` (`Type=home`, `Format=ext4`, `SizeMinBytes`/`SizeMaxBytes`) makes `systemd-repart.service` create and format the partition on the first boot — **but nothing mounts it**: with an explicit `root=PARTUUID=` the gpt-auto generator does not add `home.mount` (checked across a reboot), and the initrd's repart cannot format (no `mkfs.ext4` there). What worked: `e2fsprogs` in the image, an `/etc/fstab` line `LABEL=home /home ext4 defaults,nofail,x-systemd.device-timeout=60 0 2`, and a drop-in ordering `systemd-repart.service` `After=systemd-udevd.service` `Before=local-fs-pre.target`. Measured: repart 30 s → `home.mount` 32 s on the first boot, mounted again after reboot.
- **Where systemd-repart puts a partition it creates at boot is not yours to choose:** a size-capped runtime definition landed at the *far end* of the free space on a real disk twice (even with the preceding partition declaring `PaddingMaxBytes=0`), i.e. in the unverified region of a fake-capacity stick. Deterministic alternative: define the partition in `mkosi.repart/` so it exists in the image right after the root (copy mkosi's built-in esp/bios/root definitions from `mkosi/__init__.py` — `Type=esp Format=vfat CopyFiles=/boot:/ CopyFiles=/efi:/`, the BIOS-boot GUID at 1M, `Type=root Format=ext4 CopyFiles=/ Minimize=guess`), then let the runtime definition only **grow it in place** (`SizeMinBytes`/`SizeMaxBytes` + `GrowFileSystem=yes`, mount with `x-systemd.growfs`). A partition glued after the root means the root can no longer grow at first boot — size the root at build time instead.
- **`nofail` drops `Before=local-fs.target`**, so `systemd-tmpfiles-setup` (and anything else that only waits for local-fs) runs before the new `/home` is mounted — home directories created by tmpfiles landed under the mountpoint and vanished. Fix: create them from a oneshot ordered `After=home.mount local-fs.target` + `Wants=home.mount` + `Before=systemd-user-sessions.service <session>.service` (`systemd-tmpfiles --create <own file>`), with the session unit `After=`/`Wants=` that oneshot. Keep nothing persistent in `/home` inside the image (ssh keys → `/etc/ssh/authorized_keys.d/%u`).
- **Verify an image without mounting it:** `systemd-dissect --copy-from image.raw /etc/shadow /tmp/x` (root), `systemd-dissect --mtree image.raw | grep <path>` for modes — enough to check that a Wi-Fi profile or a password hash landed, printing only presence and lengths.
- **Passing secrets to the build:** `--environment=NAME` (name only) takes the value from mkosi's environment; export the `KEY=VALUE` lines literally (`export "$line"`) — *sourcing* the file expands `$6$` in a crypt hash as a positional parameter (`unbound variable`). Clear old outputs before the run so a failed build can never hand back a stale image.

## Running the image on real hardware — lessons (2026-10-18)
- **A `User=` service with `PAMName=login` does not own its processes:** pam_systemd puts the compositor and its children into a logind session scope, so `systemctl restart` of the unit starts a second session next to the old one (two labwc, two Chromes). Add `ExecStopPost=-/usr/bin/loginctl terminate-user <user>` to the unit.
- **Live patching a running box:** a `tar -cf - . | ssh host 'sudo tar -C / -xf -'` of the overlay tree plus `systemctl daemon-reload` applies everything that is not boot chain or partition layout; the host key changes with every re-image, so pin nothing (LAN/WireGuard only). `apt-get install` on the box needs `apt-get update` first — a mkosi image carries no package lists.
- **The image has what you listed and nothing else:** no `python3`, `lsusb`, `dmidecode`, `rsync` unless named. Decide early which admin tools belong in it.
- **First boot on slow media (USB 2.0 stick, ~9 MB/s writes):** `mkfs.ext4` of a 32 GB partition plus its lazy inode-table initialisation keeps the device at 80–100 % I/O pressure for a long time; Chrome's profile writes, journald (watchdog-killed after 3 min of blocked writes) and anything else contend. Keep benchmark loops off a box someone might use, size first-boot partitions for the medium, and treat such sticks as installers, not system drives.
- **Firmware remembers the USB boot device by port:** moving the stick to another socket left an Award BIOS waiting at a prompt on an output nobody was watching.

## Session units, a sign-in screen and testing them (2026-10-18)
- **Two units that `Conflicts=` each other must not both be `WantedBy=graphical.target`:** systemd drops one of the two jobs from the boot transaction, and which one is not stable (one build booted the right session, the next booted neither — blank console, `ConditionResult=no`, no journal line at all for the dropped unit). Use a oneshot selector (`session-select` → `systemctl start --no-block <one>`) as the only enabled unit; keep the `Conflicts=` for runtime switching.
- A kiosk Chrome under `cage` came up in a quarter of the screen after the output appeared; the same page under `labwc` with a `<windowRule identifier="*"><action name="Maximize"/>` rule fills it. Chrome `--kiosk` + `--force-device-scale-factor` works for a PIN pad page; size such pages in `vh` units so a 1280x720 logical TV fits without scrolling.
- Forced session restarts stop Chrome with SIGTERM → "Restore pages? Chrome didn't shut down correctly" on the next start; `--disable-session-crashed-bubble --hide-crash-restore-bubble` removes it.
- `sfdisk`/`wipefs`-style tools: Debian ships `sfdisk` in the **`fdisk`** package, not `util-linux`; `grub-install` is in `grub2-common`, `mkfs.vfat` in `dosfstools`, `mkfs.ext4` in `e2fsprogs` — an installer script inside the image needs all four listed.
- **Driving a QEMU guest's screen in tests:** the monitor's `sendkey 1` … `sendkey ret` types into whatever has focus (a kiosk PIN pad included), `screendump` proves what is drawn; in bash test scripts don't wrap the ssh probe in a pipe (`ssh … | grep -v x` returns grep's status — 1 on empty output — so an `until` loop never sees success).

## Headless QEMU testing on a Mac (Homebrew `qemu`)
`qemu-system-x86_64 -machine q35 -cpu max -smp 2 -m 2048 -drive file=test.raw,format=raw,if=virtio -netdev user,id=n0,hostfwd=tcp::2222-:22 -device virtio-net-pci,netdev=n0 -vga std -display none -monitor unix:monitor.sock,server,nowait -serial file:serial.log` (+ for UEFI: `-drive if=pflash,format=raw,readonly=on,file=$(brew --prefix)/share/qemu/edk2-x86_64-code.fd -drive if=pflash,format=raw,file=vars.fd` with `vars.fd` copied from `edk2-i386-vars.fd`). `screendump file.ppm` on the monitor socket + `sips -s format png` gives a screenshot without a window; ssh in through the forwarded port. QEMU's std VGA has no GL, so a wlroots compositor needs `WLR_RENDERER_ALLOW_SOFTWARE=1` to come up there. Always boot a scratch copy of the image, and `truncate` it larger when first-boot partitioning is under test. macOS has no `timeout`; loop with `until ssh … true; do sleep 5; done`.
